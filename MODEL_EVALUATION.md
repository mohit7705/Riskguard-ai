# RiskGuard AI — Model Evaluation

## Dataset

- **10,000** total return records: **8,000 legitimate**, **2,000 abusive** (20% abuse rate).
- Abuse is split evenly across five types, 400 records each:
  `WARDROBING`, `SERIAL_RETURNER`, `ITEM_SWAP_OR_EMPTY_BOX`, `ABUSE_RING`, `SUSPICIOUS_ACCOUNT_BEHAVIOR`.
- Synthetic data generated by a rule-based simulator (users → orders → items → baseline returns → injected abuse ground truth), validated against a strict schema/invariant checker before every training run.
- **Split:** stratified 80/20 train/test (`train_test_split`, `random_state=42`). Train: 8,000 rows (6,400 legitimate / 1,600 abusive). Test: 2,000 rows (1,600 legitimate / 400 abusive), held out and untouched until final evaluation.

## Data leakage fix

An earlier version of the generator drew `item_condition_score`, `vision_confidence_score`, and `package_weight_delta_pct` for `WARDROBING` and `ITEM_SWAP_OR_EMPTY_BOX` from ranges with **zero overlap** with the legitimate distribution (e.g. legitimate `vision_confidence_score ∈ [0.85, 1.00]` vs. abusive `∈ [0.05, 0.39]`). This let the model separate those two classes on a single threshold instead of learning real fraud patterns, producing artificially perfect metrics (>99.7% precision/recall).

**Fix:** widened the legitimate distribution to include a realistic low-tail (e.g. ~12% of legitimate returns now have a genuinely worn item, ~6% have a lower vision-match confidence) and narrowed the abusive ranges to the validator's actual ground-truth boundary. This created real overlap between classes, forcing the model to combine multiple weak signals rather than read one clean cutoff. The other three abuse types (`SERIAL_RETURNER`, `ABUSE_RING`, `SUSPICIOUS_ACCOUNT_BEHAVIOR`) were not affected — they rely on aggregate behavioral/network signals (return velocity, shared device/address/payment fingerprints), which are legitimately strong, non-artificial fraud signals.

## Model comparison (held-out test set, 2,000 rows)

| Metric | Random Forest | XGBoost |
|---|---|---|
| Accuracy | 98.75% | 98.80% |
| Precision | 94.54% | 96.31% |
| Recall | 99.50% | 97.75% |
| F1-score | 96.95% | 97.02% |
| ROC-AUC | 99.71% | 99.92% |
| PR-AUC | 98.18% | 99.70% |

**Confusion matrices:**

| | RF: Pred Legit | RF: Pred Abuse | | XGB: Pred Legit | XGB: Pred Abuse |
|---|---|---|---|---|---|
| **Actual Legit** | 1577 | 23 | | 1585 | 15 |
| **Actual Abuse** | 2 | 398 | | 9 | 391 |

PR-AUC is the primary comparison metric given the 20% positive class rate; ROC-AUC is reported for completeness. XGBoost was selected for production: fewer false positives (15 vs. 23, meaning fewer genuine customers wrongly flagged), higher PR-AUC, native calibration support, and native SHAP-style explainability via `pred_contribs`.

## Cost-based decision threshold

Rather than defaulting to a 0.5 probability cutoff, the decision threshold is chosen to minimize expected business cost:

- **False positive** (wrongly flagging a genuine customer): lost goodwill, support overhead.
- **False negative** (missing real abuse): refund + item value walks out the door.

The threshold-vs-cost tradeoff is computed by sweeping the precision-recall curve on a held-out calibration split and selecting the threshold with minimum expected cost, visualized live on the Risk Reports dashboard (Threshold vs. Cost Tradeoff chart).

## Explainability

Per-case explanations use XGBoost's native TreeSHAP implementation (`Booster.predict(..., pred_contribs=True)`), not the `shap` package — as of `xgboost>=3.0`, `shap.TreeExplainer` fails on a known, currently-unresolved upstream incompatibility (`base_score` serialized as a JSON list; see `shap/shap#4288`, `shap/shap#4202`). XGBoost's native contribution computation is the same exact TreeSHAP algorithm, computed in C++, without depending on the affected code path. Falls back to static global feature importance if no usable booster is available.

## Defense-only scope

RiskGuard AI scores and flags return requests for human review or block decisions. It takes **no autonomous action** against users, accounts, or payments — every BLOCK/ALLOW outcome above the review threshold is subject to analyst confirmation via the Review Queue.
